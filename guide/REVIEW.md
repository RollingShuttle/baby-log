- [ ] **store_js/F1 · major** — A phone that could not pull numbers its edit from a stale base, and the collision is settled silently by created_at — a PC deletion or edit is undone (or the phone's edit dropped) with no notice
  - `store.js:324`
  - Scenario: MSAL refresh tokens for the phone last 24 h, so each phone is 'Signed out' for hours most days while logging keeps working (§7.6). 1) Mom's phone holds feed X at r1 and is signed out since 20:00. 2) At 02:00 Dad deletes X on the PC: tombstone r2, created_at 02:00. 3) At 03:00 Mom opens X (her phone still shows it live) and changes the note. `pullIfStale` does not fire (last_sync_at is 7 h old, the guard is `> DAY`), `guardOther` only guards Switch/Stop, so `Store.revise` builds `revision: cur.revision + 1` = r2 from the r1 base with created_at 03:00 and queues it. 4) At 07:00 Mom signs in: `Sync.run` does `flush()` first, uploading her r2; then `pull()` downloads the PC's r2; `applyRemote` runs `Core.resolve([held, rec])` — same revision, neither ended, her created_at is later, so hers wins and applyRemote returns false. On the PC `resolve` picks the same winner: the deleted feed is back in the day sheet and Settings → Deleted no longer lists it. Nobody is told; the tombstone is visible only in the PC history view. The mirror case is as common: Dad stops the running feed on the PC (r2, end set) while Mom, signed out, types a note on it (r2, end null) — the end rule makes the PC win and Mom's note vanishes silently after the next sync.
  - Evidence: `store.js: `return saveEvent(eventRecord({ event_id: cur.event_id, revision: cur.revision + 1 }, fields || {}, cur));`  sync.js: `return Number.isNaN(at) || now - at > DAY;` (stalePull)  sync.js run(): `result.flush = await flush();\n          result.pull = await pull();``

(Also drop the 24 h threshold in `stalePull` to "older than the last successful pull that saw this record" or simply run the pull whenever `last_sync_at` is older than the poll interval.)
  - **Skeptic's better fix (use this):** Keep the spec's flush-then-pull order (§7.3 after-write, §7.6 first sign-in) and the §3.4 winner — do not move the pull ahead of the flush and do not add a new `conflict` queue state. Minimal change: in Sync.pull/applyRemote, when a downloaded record has the same revision as the held one, a different `device`, and the queue (or a just-flushed set kept for the run) contains an item for that id, push the id onto a `counts.conflicts` list; emit it with the existing `applied` event so app.js can show the existing `Updated from <whose>`/`Deleted on <whose>` line as a toast (not only inside an open editor) and list the ids under Settings → sync details. Independently, drop stalePull's threshold from 24 h to a few poll intervals (e.g. 5 min) so a signed-in phone pulls before a revise far more often.
